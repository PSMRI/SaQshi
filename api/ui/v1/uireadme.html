SaQshi UI Service v1

1. Purpose

The SaQshi UI Service provides a frontend-friendly, stateless API layer for building assessment user interfaces on top of the SaQshi platform.

These APIs are designed for:

  • Web Applications
  • Mobile Applications (Android / iOS)
  • Government & Partner Systems

The UI Service hides all database and business logic. Integrators interact only with stable JSON APIs.

2. Architecture Overview

UI / Mobile App
      ↓
SaQshi UI Service (this layer)
      ↓
Assessment Service (business logic)
      ↓
Database
Important: UI applications must never directly access database tables or stored procedures.

3. Base URLs

Local / Development

http://localhost:94/api/ui/v1

Production (Example)

https://api.saqshi.in/api/ui/v1

4. Authentication

UI APIs are currently open for ease of integration.

Authentication (API Key / Token / OAuth2) can be enabled later without changing API contracts.

5. Assessment Lifecycle APIs

5.1 Start / Resume Assessment

GET /assessment/start 
/assessment/start?facility_id=1&department_id=2&assessment_period=2024

Response

{
  "status": "success",
  "data": {
    "completed": false,
    "subtype_id": 14,
    "csqa_id": 233
  }
}

5.2 Get Single Checklist Question

GET /assessment/checkpoint 
/assessment/checkpoint?csqa_id=233

5.3 Save Checklist Response

POST /assessment/save 
{
  "facility_id": 1,
  "department_id": 2,
  "assessment_period": 2024,
  "csqa_id": 233,
  "compliance": 2,
  "user_id": 15
}

5.4 Resume / Next Question

GET /assessment/resume 
/assessment/resume?facility_id=1&department_id=2&assessment_period=2024

6. Progress & Navigation APIs

6.1 Overall Assessment Progress

GET /assessment/progress 
/assessment/progress?facility_id=1&assessment_period=2024

6.2 Subtype-wise Progress

GET /assessment/subtype-progress 
/assessment/subtype-progress?
facility_id=1&
department_id=2&
assessment_period=2024&
facility_type=3&
concern_id=4

6.3 Concern-wise Progress

GET /assessment/concern-progress

7. Completion API

7.1 Mark Assessment Complete

POST /assessment/complete 
{
  "facility_id": 1,
  "department_id": 2,
  "assessment_period": 2024,
  "user_id": 15
}
Once completed, assessments can optionally be locked from further edits.

8. Master Data APIs

8.1 Areas of Concern

GET /masters/concerns

8.2 Subtypes by Concern

GET /masters/subtypes 
/masters/subtypes?concern_id=3&facility_type=2

9. Standard Response Format

{
  "status": "success",
  "message": "Optional message",
  "data": {...}
}

Error Format

{
  "status": "error",
  "message": "Reason for failure"
}

10. HTTP Status Codes

CodeMeaning
200Success
400Invalid or missing parameters
401Unauthorized (future)
500Server error

11. Design Principles

  • Stateless APIs
  • JSON-only communication
  • Rule-based calculations (no derived storage)
  • Versioned endpoints
  • Reusable across applications
  • DPG-compliant architecture
